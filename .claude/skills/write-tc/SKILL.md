# write-tc — 테스트 케이스 설계

QA 관점에서 기능마다 정상 · 경계 · 예외 · 보안 케이스를 빠짐없이 설계한다.

## 순서

1. `CLAUDE.md`의 핵심 흐름과 "안정성" 목록, 그리고 기존 `docs/qa/test-cases.md`를 읽는다.
2. 대상 기능에 대해 아래 관점으로 케이스를 뽑는다:
   - **정상**: 대표 입력으로 끝까지 도는가
   - **경계**: 빈 값, 최소·최대 길이, 용량 한계, 특이한 형식(전화번호 띄어쓰기, 영문 공고 등)
   - **예외**: 잘못된 형식, 공고가 아닌 입력, API 실패·지연·깨진 응답, 중간 이탈
   - **보안**: 개인정보가 화면·로그·API 요청에 남는지, 키가 노출되는지
3. 이미 있는 TC와 겹치면 새로 만들지 않고 기존 TC를 고친다.
4. 기존 표 형식 그대로 해당 영역 섹션에 추가한다. ID는 영역 번호 체계를 따른다 (공통 0xx, 입력 1xx, 마스킹 2xx, 질문 3xx, 답변 4xx, 모의면접 5xx, 내보내기 6xx, API 7xx).
5. 맨 위 "요약" 표의 개수를 다시 센다.

## 작성 규칙

- **기대 결과는 관찰 가능한 문장으로** 쓴다. "잘 동작한다" (X) → "에러 안내와 다시 시도 버튼이 보인다" (O)
- 한 TC는 한 가지만 확인한다.
- 자동화 칸: 화면에서 결정적으로 확인 가능하면 E2E, AI 출력 품질이면 평가, 사람 판단이 필요하면 수동.
- AI 출력(질문, 답변)은 내용이 매번 달라지므로 E2E에서는 **데모 모드 고정 결과**나 **route mock**으로 확인한다고 적는다.
- 우선순위: 핵심 흐름이 멈추면 P1, 기능 일부 오류 P2, 불편 P3.

## 끝나면

새로 추가하거나 바꾼 TC ID 목록과, 그중 E2E로 자동화할 TC를 알려 주고 `e2e-test` 스킬로 이어서 자동화할지 묻는다.
