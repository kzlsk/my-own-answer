## CLAUDE.md · 스킬 활용

- 1일차: `CLAUDE.md`에 서비스 흐름, 범위 밖 기능, API 키 규칙, 안정성 목록, 지표, QA 규칙을 정리해 매 작업의 기준으로 사용
- 1일차: 프로젝트 전용 스킬 5개를 만듦

| 스킬 | 만든 이유 | 효과 (작업하며 채움) |
| --- | --- | --- |
| `make-test-data` | 가상 데이터에 실제 개인정보가 섞이지 않게, 까다로운 경우가 빠지지 않게 | |
| `run-eval` | v1·v2를 매번 같은 세트, 같은 형식으로 평가하려고. 채점은 사람이 하도록 못 박음 | |
| `log-prompt` | 프롬프트 변경 이유와 수치를 빠짐없이 남기려고 | |
| `write-tc` | 기능 구현 전에 정상·경계·예외·보안 케이스를 먼저 설계하려고 | |
| `e2e-test` | TC와 자동화 테스트를 ID로 연결하고, 테스트를 억지로 통과시키지 않게 | |

## AI 실수와 수정 사례

| 날짜 | AI가 한 실수 | 어떻게 발견했나 | 어떻게 고쳤나 |
| --- | --- | --- | --- |
| 1일차 | (서비스 AI) answer-v1이 맞는 경험이 없는 질문에 없는 학습 이력·QA 경험을 지어냄 (12문장) | 문장 단위 채점 (`data/results/2026-10-29-answer-v1`) | answer-v2에서 근거를 경험 답변·이력서로 제한하고, 없는 경험은 인정 후 가까운 경험으로 연결하게 함 |
| 1일차 | (서비스 AI) 마스킹 토큰 `[이름]`을 답변에 그대로 씀 ("저는 [이름]입니다") | 채점 중 발견, BUG-001 | answer-v2에 인사·이름 소개·가림 토큰 금지 추가. 화면 단계에서도 후처리 검토 |
| 2일차 | (개발 AI) E2E 테스트가 `getByRole("alert")`로 오류 안내를 찾았는데, Next.js가 넣는 숨은 route announcer도 role="alert"라 두 개가 잡힘 (12개 실패) | E2E strict mode 위반 메시지 | 화면 오류 안내만 찾는 `alertBox()` 선택자로 교체. 앱 코드는 문제 없었음 |
| 2일차 | (개발 AI) `getByLabel("내 경험")`, `getByText("경험을 먼저 적어 주세요.")`가 섹션 제목·설명문까지 같이 잡음 | 같은 strict mode 위반 | `getByRole("textbox", { name })`, 고유 id(`#experience-hint`)로 대상 한정 |
| 2일차 | (개발 AI) 공고 판별 패턴이 스타트업식 공고 제목("이런 일을 해요")을 몰라서 실제 공고를 막음 | 수집한 공고 6개로 돌린 단위 테스트, BUG-002 | 패턴 추가 후 공고 6개 통과, 이력서 5개는 계속 차단 확인 |
| 2일차 | (개발 AI) "인쇄 → PDF면 글자가 남는다"고 가정하고 안내 문구를 씀. Windows 'Microsoft Print to PDF'는 글자를 그림으로 저장 | 실제 잡코리아 공고로 써 보다가 발견, `pdfinfo`·`pdffonts`로 원인 확인 (BUG-004) | 글자 없는 PDF는 페이지를 이미지로 바꿔 자동 판독, 안내 문구 수정 |
| 2일차 | (개발 AI) 마스킹이 "이름: ○○○" 형식만 처리했고, 테스트용 가상 이력서도 같은 형식으로 만들어 테스트가 통과함 | 실제 이력서로 확인하다 이름·생년월일이 남는 것을 발견 (BUG-005) | 제목 줄·파일 이름에서 이름 찾기, 생년월일, 직접 가릴 단어 추가. 실제 형식을 흉내 낸 가상 데이터로 테스트 보강 |
| 2일차 | (개발 AI) BUG-005를 고치며 넣은 이름 패턴이 줄바꿈을 넘어 다음 줄 단어("복약")를 이름으로 가림 | 정리 평가 스크립트 dry-run 결과 파일을 직접 열어 봄 (BUG-006) | 같은 줄 안에서만 찾게 수정, 오탐 방향 단위 테스트 추가 |
| 3일차 | (개발 AI) 꼬리질문 평가의 "정상 답"으로 이력서의 경험 목록 전체를 넣음. 질문과 맞지 않는 답이라 면접관이 "다시 답해 달라"고 하는 게 자연스러워 평가가 불공정 | v1 결과를 채점하다 발견 | 정상 답을 그 질문에 맞춘 답변 초안(answer-v2 결과)으로 바꿈. v1도 바뀐 평가로 다시 측정 |
| 3일차 | (개발 AI) 평가 스크립트가 결과 폴더를 "날짜-버전"으로만 만들어, 같은 날 다시 실행하자 채점해 둔 scoring.csv를 덮어씀 | 2차 실행 결과를 가져오다 1차 라벨이 사라진 것을 발견 | 1차 결과를 run1 폴더로 복구, 같은 폴더가 있으면 -run2, -run3로 새로 만들도록 수정 |
| 3일차 | (개발 AI) 클라우드 E2E가 모두 통과해서 개발 서버 새로고침 문제를 못 잡음. 사용자 PC(OneDrive 폴더)에서만 첫 API 호출마다 페이지가 새로고침됨 | 사용자 제보 → Claude 브라우저로 사용자 PC의 localhost에서 재현, Console·Network로 원인 확인 (BUG-008) | 개발 서버를 Turbopack으로, 프로젝트를 OneDrive 밖으로 옮기도록 안내 |
| 3일차 | (개발 AI) 결과 HTML 파일 이름을 한글(`면접준비_날짜.html`)로 정함 | E2E에서 내려받은 파일 이름이 "download"로 바뀜 (TC-601) | 영문 `my-own-answer_날짜.html`로 변경. 환경에 따라 한글 다운로드 이름이 보존되지 않을 수 있음 |
| 3일차 | (개발 AI) Markdown 채점 함수가 "**제목**"의 첫 `*`를 목록 기호로 지움 | 채점 함수 단위 테스트(TC-125)를 먼저 써서 발견 | 굵게 표시를 먼저 지우도록 순서 변경 |
| 2일차 | (개발 AI) 긴 스크린샷을 1,800px로 잘라 "뭉개지지 않게" 했다고 판단. OpenAI가 조각의 짧은 변을 다시 768px로 줄이는 것은 확인하지 않음. 판독 모델도 앱 기본(gpt-4o-mini) 그대로 둠 | 실제 공고 캡처 판독 결과를 원문과 비교 (BUG-007, 글자 정확도 76.2%) | 조각 높이 768px, 판독만 gpt-4o, 프롬프트 v2, 정확도 측정 스크립트 추가 |
| 2일차 | (개발 AI) E2E가 데모 질문 문구("커머스 서비스의…")에 의존해서, 데모 샘플을 다시 만들면 깨지는 구조 | 데모 생성 스크립트를 만들면서 발견 | ★(데모 체험 가능) 질문을 접근성 이름으로 찾도록 바꿔 문구와 무관하게 동작 |

| 판단 | 맞바꾼 것 | 이유 |
| --- | --- | --- |

| 자동 마스킹에 "더 가릴 단어" 직접 입력을 더함 | 자동 마스킹만 사용 | 팀원 이름·사내 프로젝트명은 규칙으로 찾기 어려움. 사용자가 "AI에 보내는 이력서"를 보고 직접 보완 |
| 형식이 다른 이력서를 AI가 정해진 섹션으로 정리 (경력·프로젝트[트러블슈팅 포함]·기술 스택·교육·활동·자격증·수상) | 가린 원문을 그대로 사용 | 피그마·노션·원티드 등 형식이 달라도 뒤 단계 입력을 고르게 맞춤. 트러블슈팅은 맥락이 끊기지 않게 프로젝트 안에 둠 |

| 모의면접은 답변 초안을 만든 질문으로만 진행 | 모든 예상 질문으로 진행 | 경험을 먼저 적은 질문이어야 피드백이 "준비한 초안에 있는데 말하지 않은 것"을 짚을 수 있음 |
| 데모 모드 모의면접은 정해 둔 꼬리질문·피드백 | 데모에서 규칙만 동작 | 배포 사이트에서도 흐름을 끝까지 체험. 대신 데모라는 안내를 화면에 표시 |
| 결과 내보내기는 브라우저에서 만들고 이력서 내용은 넣지 않음 | 서버에서 파일 생성 / 이력서 포함 | 서버에 결과가 남지 않고, 공유하기 쉬운 문서에 개인정보가 섞이지 않음 |
| HTML 내보내기의 모든 글은 이스케이프 (TC-604) | AI 출력을 그대로 넣음 | 사용자가 적은 글이나 AI 출력에 태그가 섞여도 저장한 파일을 열 때 실행되지 않음 |
| 화면을 한 페이지 세로 흐름에서 단계형 워크스페이스로 (준비 → 질문과 답변 → 모의면접 → 결과 정리) | 한 페이지에 카드 6개 | 질문이 9개, 초안·면접 기록이 쌓이면 스크롤이 너무 길어짐. 질문 목록과 작업 영역을 나란히 두면 질문을 오가며 초안을 고치기 쉬움 |
| 질문과 면접관의 말은 명조(Noto Serif KR), 내가 쓰는 글은 고딕(Pretendard). 강조색은 파랑 하나, "내 경험"에만 형광펜 | 기본 Tailwind 색(teal)과 시스템 글꼴 | 질문지·면접 대본처럼 읽히게 하고, 서비스 핵심인 "내 경험"이 어디 있는지 눈에 띄게 함 |
| 글꼴은 npm 패키지(pretendard, @fontsource/noto-serif-kr)로 넣음 | Google Fonts 링크 | 빌드할 때 외부 다운로드가 없어 오프라인·차단된 네트워크에서도 빌드됨 |
| 단계를 옮겨도 화면을 지우지 않고 숨기기만 함 | 단계마다 새로 그리기 | 면접 중에 초안을 보러 갔다 와도 면접 대화가 그대로 남음 |
| 답변 초안을 화면에서 직접 고칠 수 있게 하고, 고친 내용을 모의면접·내보내기에 씀 | 생성된 초안을 그대로 사용 | 초안은 출발점일 뿐이고 최종 답은 내가 다듬어야 함 |
| 내보내기에서 준비하지 않은 질문은 맨 아래 한 목록으로 | 질문마다 "아직 준비하지 않은 질문" 칸 | 실제 준비한 내용이 먼저 보이게 |
| 꼬리질문은 v2를 채택하되 지어냄 1건(모호한 답)은 남은 위험으로 기록 | v3까지 만든 뒤 채택 / v1 유지 | 실제 사용에서 대부분인 정상 답에서 효과가 크고(40%→80%), v1도 관련 있는 답을 잘라 내는 문제가 있었음. 남은 문제는 수치와 함께 숨기지 않고 기록 |
| 무관한 답일 때 다시 요청 문구는 모델 대신 정해 둔 문구 | 모델이 쓴 문구 사용 | v2 평가에서 어색한 문구가 나옴. 같은 상황에는 같은 말이 나오는 편이 사용자에게도 테스트에도 좋음 |
| 모호한 답에는 모델이 문장을 쓰지 않고 이력서 항목 이름만 고르게 하고, 다시 묻는 문장과 항목 검증(이력서에 그 글자가 있는지)은 코드가 함 (interviewer-v3) | v2처럼 모델이 꼬리질문 문장을 직접 씀 | v2에서 "말하지 않은 경험 전제 금지" 규칙이 있어도 모호한 답에 경험을 지어냄. 지어낼 수 있는 자리(자유 문장)를 없애고, 남는 자리(항목 이름)는 이력서와 대조해 막음 |
| 평가 결과를 "모델이 한 말"이 아니라 "앱이 실제로 할 말"(decide 함수를 거친 결과)로 채점 | 모델 출력 그대로 채점 | 사용자가 보는 건 앱이 거른 결과. 라우트와 평가 스크립트가 같은 decide()를 써서 평가와 실제 동작이 어긋나지 않음 |
| 꼬리질문 프롬프트를 v1 → v4까지 네 번 고치며, 매번 같은 평가(정상 답 1 + 모호한 답 2 × 5개 조합)로 재고 채택 | 한 번에 완성된 프롬프트를 쓰려 함 | 평가해 보기 전에는 몰랐던 문제(질문 되풀이 → 모호한 답에 경험 지어냄 → 정상 답 오판)가 버전마다 하나씩 드러남. 수치로 비교했기 때문에 v3처럼 "지어냄은 막았지만 다른 게 나빠진" 경우를 채택하지 않을 수 있었음 |
