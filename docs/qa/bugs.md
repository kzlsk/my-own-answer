### BUG-002 스타트업식 표현으로 쓴 실제 채용공고를 "채용공고가 아니다"로 막음

- **심각도**: Major (해당 공고로는 질문 생성 자체를 할 수 없음)
- **관련 TC**: TC-106
- **환경**: `src/lib/posting.ts` (공고 판별 함수), 2일차
- **발견자 · 날짜**: 단위 테스트 `[TC-106] 수집한 공개 공고 6개는 모두 공고로 판별된다` · 2일차

**재현 절차**

1. 채용공고 칸에 `data/postings/p02-backend.md`(당근마켓 백엔드) 본문 붙여넣기
2. 예상 질문 만들기 클릭

**기대 결과**

**실제 결과**

**근거**

**수정 내용 · 확인**

- "이런 일을 / 함께할 업무 / 합류하면", "이런 분을·과·이면 / 기다리고 있어요 / 함께하고 싶어요", "포지션 / 모집 분야" 패턴 추가
- 수정 후 신호 개수: p02 = 5개, 이력서 5개는 모두 1개 (이력서를 공고 칸에 넣은 경우는 계속 막힘)

- 배운 점: 거르는 기능은 "막아야 할 것"뿐 아니라 "통과해야 할 실제 데이터"로도 테스트해야 한다

### BUG-003 업로드 제한(5MB)이 Vercel 요청 한도(4.5MB)보다 커서 배포 환경에서만 실패

- **심각도**: Major (화면은 "업로드 가능"이라고 안내하는데 배포 사이트에서는 요청 자체가 거부됨)
- **관련 TC**: TC-105
- **환경**: Vercel 배포 환경 (로컬 `npm run dev`에서는 재현되지 않음)
- **발견자 · 날짜**: 본인 · 2일차 (공고 스크린샷 업로드를 설계하며 요청 크기를 확인하다 발견, 배포 전 예방)

**재현 절차 (예상)**

1. Vercel에 배포된 사이트에서 4.6MB짜리 PDF 이력서 올리기

**기대 결과**

업로드되거나, 올리기 전에 용량 안내가 보인다.

**실제 결과 (예상)**

화면 검사(5MB 이하)는 통과하지만 Vercel이 4.5MB를 넘는 요청을 거부해 일반 오류만 보인다.

**원인**

화면·서버 용량 제한을 5MB로 정할 때 배포 플랫폼의 요청 본문 한도를 고려하지 않음.

**수정 내용 · 확인**

- `src/lib/limits.ts`의 업로드 제한을 4MB로 낮추고, 안내 문구도 같은 값을 쓰게 통일 (`tooLargeMessage()`)
- 공고 스크린샷은 브라우저에서 가로 1,400px로 줄여 JPEG로 보내고, 합계가 4MB를 넘으면 보내기 전에 안내
- 다시 실행한 테스트: E2E `[TC-105]` (4MB + 1바이트) Pass → **Fixed**
- 배운 점: 로컬과 배포 환경의 제한이 다른 경우를 TC 사전조건에 적어야 한다

### BUG-004 'Microsoft Print to PDF'로 저장한 공고 PDF를 읽지 못함

- **심각도**: Major (복사가 막힌 공고를 가져오는 주 경로가 Windows 기본 설정에서 실패)
- **관련 TC**: TC-109, TC-115 (신규)
- **환경**: Windows, 잡코리아 공고, 인쇄 대상 'Microsoft Print to PDF'
- **발견자 · 날짜**: 본인 · 2일차 (실제 잡코리아 공고로 써 보다가 발견)

**재현 절차**

1. 잡코리아 공고 페이지에서 `Ctrl+P` → 대상 'Microsoft Print to PDF'로 저장
2. "공고 PDF 올리기"로 올리기

**기대 결과**

공고 글자가 공고 칸에 채워진다.

**실제 결과**

"PDF에서 글자를 찾지 못했습니다. 공고가 이미지로 되어 있다면 '스크린샷으로 가져오기'를 써 주세요." 안내만 뜬다.

**근거**

`pdfinfo`: Producer = "Microsoft: Print To PDF" / `pdffonts`: 글꼴 0개 / `pdftotext`: 빈 결과 / `pdfimages`: 4쪽에 이미지 7장. 페이지 전체가 그림으로 저장되어 글자 층이 없음.

**원인**

- 'Microsoft Print to PDF'는 페이지를 그림으로 찍어 저장하는데, 크롬의 'PDF로 저장'은 글자를 남김. 이름이 비슷해 사용자가 구분하기 어려움
- 설계할 때 "인쇄 → PDF면 글자가 남는다"고 가정했고, 안내 문구에도 이 차이가 없었음 (AI가 쓴 안내 문구를 실제 Windows 환경에서 확인하지 않음)
- 글자 없는 PDF를 만나면 에러로 끝나서, 사용자가 다시 캡처해야 했음

**수정 내용 · 확인**

- 서버: 글자 없는 PDF를 받으면 키가 있을 때 `PDF_NEEDS_OCR`로 응답 (데모 모드에서는 'PDF로 저장'으로 다시 저장하라는 안내)
- 화면: `PDF_NEEDS_OCR`을 받으면 PDF 페이지(최대 4쪽)를 브라우저에서 이미지로 그려 스크린샷 판독 경로로 자동 재전송
- 이미지 자르기: 페이지 끝 400px 이하 남는 부분(인쇄 머리글·바닥글)은 앞 조각에 붙여서 A4 한 쪽 = 한 조각. 실제 공고 PDF 4쪽 → 8조각에서 4조각으로 줄어 조각 한도(8) 여유 확보
- 안내 문구에 "'Microsoft Print to PDF'는 고르지 마세요" 추가
- 실제 공고 PDF로 확인: 4쪽 → 이미지 4조각(약 390KB)으로 전송, 이미지에서 담당업무·자격요건·우대사항이 선명하게 보임 (실제 판독 정확도는 TC-114에서 키로 확인)
- 다시 실행한 테스트: E2E `[TC-109]`, `[TC-115]`, `[TC-111]` 포함 전체 50개 Pass → **Fixed**
- 배운 점: 파일 형식이 같아도 만드는 도구에 따라 내용이 다르다. 사용자 환경(OS 기본 설정)으로 만든 실제 파일을 테스트 데이터에 넣어야 한다

### BUG-005 실제 이력서의 이름·생년월일이 가려지지 않고 AI로 전송됨

- **심각도**: Critical ("AI에 보내기 전에 가려진다"고 안내하는데 실제로는 이름과 생년월일이 외부 AI로 나감)
- **관련 TC**: TC-203, TC-204, TC-205, TC-117 (신규)
- **환경**: 디자인 도구로 만든 실제 PDF 이력서 (4쪽, 5.36MB, 이미지 58장)
- **발견자 · 날짜**: 본인 · 2일차 (실제 이력서로 업로드 용량을 확인하다가 발견)

**재현 절차**

1. 첫 줄이 "Frontend Developer 홍길동", 둘째 줄이 "2001. 05. 17 | 이메일 | 전화 | GitHub"인 이력서 PDF 올리기
2. 가린 개인정보 표시와 "AI에 보내는 이력서 보기" 확인

**기대 결과**

이름·생년월일·이메일·전화·링크가 모두 가려진다.

**실제 결과**

이메일·전화·링크만 가려지고 **이름 0개**, 생년월일은 대상이 아니라 그대로 남음. 팀원 이름도 남음. 또 모든 줄이 두 번씩 추출됨("IntroIntro").

**근거**

실제 이력서 추출 결과: 5,499자, 마스킹 결과 `{"name":0,"phone":2,"email":2,"url":6}`. 이름이 5번 나오지만 "이름:" 표시는 없음.

**원인**

- 이름을 "이름: ○○○" 줄에서만 찾았음. 테스트용 가상 이력서 5개가 모두 그 형식이라 테스트가 통과했음 (테스트 데이터가 실제 형식을 대표하지 못함)
- 생년월일은 마스킹 대상에 없었음
- 디자인 도구 PDF는 글자 층이 겹쳐 같은 줄이 두 번 붙어 나옴

**수정 내용 · 확인**

- 이름: 첫머리 제목 줄의 "직무 + 이름"과 파일 이름("FE_이름_이력서.pdf")에서도 찾아 본문 전체를 가림. "개발자 입니다" 같은 말은 제외 목록으로 거름
- 생년월일: "생년월일:" 표시가 있으면 어디서든, 없으면 첫머리 400자 안의 연·월·일 날짜를 가림. 경력 기간("2022.07.01 - 2024.03.31")은 남김
- 직접 가릴 단어: 팀원 이름처럼 자동으로 찾기 어려운 단어를 사용자가 입력해 가림
- 겹친 줄: 같은 글이 두 번 붙은 줄은 한 번으로 줄임 (5,499자 → 5,305자)
- 실제 이력서로 화면에서 재확인: 이름 4·생년월일 1·전화 1·이메일 1·링크 5 가림, 경력 기간 날짜 28개 유지, 팀원 이름은 직접 입력 후 가림
- 실제 이력서는 저장소에 넣지 않고, 같은 구조의 가상 데이터로 단위·E2E 테스트 작성. 확인에 쓴 사본은 바로 삭제
- 다시 실행한 테스트: 단위 17개, E2E 58개 모두 Pass → **Fixed**
- 배운 점: 가상 테스트 데이터는 내가 정한 형식만 담는다. 개인정보 처리는 실제 문서 형식(디자인 도구 PDF, 제목 줄 이름)으로 꼭 확인해야 한다

### BUG-007 공고 스크린샷 판독이 문단을 빼고 단어를 다른 단어로 바꿔 적음

- **심각도**: Major (바뀐 단어가 그대로 예상 질문에 들어감. "목업" → "목욕", "서드파티" → "소프트웨어"처럼 뜻이 바뀌어 사용자가 놓치기 쉬움)
- **관련 TC**: TC-114, TC-111 (변경), TC-125 (신규)
- **환경**: Windows / Chrome / 실제 키, 판독 모델 gpt-4o-mini, 프롬프트 posting-ocr-v1
- **발견자 · 날짜**: 본인 (실제 공고 캡처로 써 보다가) · 2일차

**재현 절차**

1. 실제 공고 화면 캡처(`data/postings-image/i01-medai-frontend.png`, 1,258×1,029px)를 **공고 스크린샷 올리기**로 올림
2. 공고 칸에 채워진 글을 원문과 비교

**기대 결과**

회사 소개부터 우대사항까지 화면 글자 그대로 옮겨짐.

**실제 결과** (`data/results/2026-10-29-ocr-v1/summary.md`)

- 글자 정확도 **76.2%** (편집 거리 122 / 정답 512자), 틀린 구간 9곳
- 맨 위 회사 소개 문단 전체 누락
- 단어 바뀜: 의료→외로, 목업→목욕, 서드파티→소프트웨어, 완료된→완화된, 렌더링→렌딩, AI결과를→결과들을
- 원문 오타 "리자인"을 "리 디자인"으로 고침, 표를 "## 제목 + 중첩 목록"으로 바꿈

**원인**

1. 판독 모델: 별도 지정이 없으면 앱 기본 모델(gpt-4o-mini)을 써서 한글 글자를 모양이 비슷한 단어로 짐작함
2. 이미지 크기: OpenAI는 detail:high 이미지의 짧은 변을 768px로 줄임. 이 캡처는 짧은 변 1,029px → 75% 크기로, 기존 1,400×1,800 조각은 55% 크기로 줄어 글자가 작아짐. BUG-004 때 "긴 이미지는 잘라야 뭉개지지 않는다"까지만 보고, 잘린 조각도 다시 줄어드는 것은 확인하지 않음
3. 프롬프트 v1이 "옮겨 적기"보다 "정리"를 막는 규칙이 약해, 모델이 구조를 바꾸고 문단을 생략함

**수정 내용 · 확인**

- 판독 모델 기본값을 gpt-4o로 분리 (`VISION_MODEL`, `.env.local`의 `OPENAI_VISION_MODEL`로 변경 가능). 나머지 기능은 gpt-4o-mini 유지
- 조각 높이 1,800 → 768px (짧은 변이 768px를 넘지 않아 다시 줄지 않음). 조각 한도 8 → 16 (A4 4쪽 = 12조각)
- posting-ocr-v2: 첫 줄부터 빠짐없이, 한 글자씩 보고 적기, 비슷한 단어로 메우지 말고 [판독 불가], 오타·띄어쓰기 고치지 않기, 화면 줄 단위 유지, 표 읽는 순서 지정
- 정확도를 숫자로 재는 `npm run eval:ocr` 추가 (실제 화면 경로로 판독 → 정답과 글자 단위 비교). 채점 함수 단위 테스트 TC-125
- TC-111: 모든 조각의 짧은 변이 768px 이하인지 JPEG 크기를 직접 읽어 확인하도록 강화
- 다시 실행한 테스트: 단위 27개, E2E 66개 모두 Pass → **Fixed (재측정 대기)**. v2 정확도는 키로 `npm run eval:ocr` 실행 후 기록
- 배운 점: 외부 API가 입력을 어떻게 다시 가공하는지(이미지 리사이즈) 문서로 확인하지 않으면, 우리 쪽 전처리를 고쳐도 효과가 없을 수 있다

### BUG-008 개발 서버에서 처음 부르는 API마다 페이지가 새로고침돼 입력이 사라짐

- **심각도**: Major (이력서·공고를 다시 넣어야 하고, 사용자는 "버튼을 누르면 다 지워진다"로 느낌. 배포 환경은 해당 없음)
- **관련 TC**: TC-101, TC-301
- **환경**: Windows / OneDrive 동기화 폴더(바탕 화면) / `next dev`(webpack) / 실제 키
- **발견자 · 날짜**: 본인 (예상 질문 만들기를 누르면 입력이 사라진다고 제보) · 3일차

**재현 절차**

1. `npm run dev`를 새로 켬
2. 샘플로 체험하기(또는 이력서·공고 입력) → 예상 질문 만들기

**기대 결과**

입력이 유지되고 다음 단계가 나온다.

**실제 결과**

페이지가 통째로 새로고침되고 이력서·공고가 비어 있음. 같은 서버에서 두 번째 시도부터는 정상.

**근거** (Claude 브라우저로 본인 PC의 localhost:3000에서 재현)

- Console: `[Fast Refresh] rebuilding` → `Failed to load resource: 404`
- Network: `/api/sample` 다음 `…webpack.hot-update.json → 404`, 이어서 `GET /` 다시 요청(새로고침). `/api/resume/structure` 요청은 응답 없이 끊김
- 페이지에 표시해 둔 값(`window.__marker`)이 사라짐 = 새로고침 확인. 같은 동작을 다시 하면 표시가 유지되고 정상 동작

**원인**

개발 서버는 API를 처음 부를 때 그 라우트를 컴파일하고, 이때 화면 쪽에도 갱신(HMR) 신호를 보냄. 이 PC에서는 갱신 파일(`hot-update.json`)을 찾지 못해(404) Next.js가 페이지 전체를 새로고침함. 같은 코드가 클라우드 테스트 환경(리눅스)에서는 재현되지 않아, OneDrive 동기화 폴더의 `.next` 파일 처리(이전 `readlink EINVAL` 오류와 같은 계열)로 판단. 앱 코드 문제는 아니고 상태를 메모리에만 두는 구조라 새로고침에 그대로 날아감.

**수정 내용 · 확인**

- 개발 서버를 Turbopack으로 실행 (`next dev --turbopack`): webpack의 hot-update 파일 방식을 쓰지 않음. 클라우드에서 E2E 84개 Pass
- 권장: 프로젝트를 OneDrive 밖(예: `C:\dev\my-own-answer`)으로 옮기고 `.next` 삭제
- 배포(Vercel)·`npm run build && npm start`는 HMR이 없어 해당 없음
- 본인 PC에서 서버를 다시 켠 뒤 같은 절차로 재확인 예정
- 배운 점: "처음 한 번만 실패"하는 문제는 환경(컴파일·캐시)을 먼저 의심하고, 새로고침 여부는 페이지에 표시값을 심어 두고 확인하면 빠르다
