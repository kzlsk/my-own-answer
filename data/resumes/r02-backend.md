## 사례 1: 예매 오픈 시 좌석 중복 판매

2021.02 - 2021.04 | 무대티켓 좌석 선점 API | Spring Boot, Redis, MySQL, nGrinder

**Problem**
- 인기 공연 예매가 열리는 순간 동시 접속 약 4,000명
- 같은 좌석이 두 사람에게 팔리는 사고가 공연 1회에 3~5건 발생 → 수동 환불·사과 연락

**Process & Solution**
- 로그 분석 → 좌석 상태 조회와 변경 사이에 다른 요청이 끼어드는 것이 원인
- Redis 분산 락으로 좌석 단위 선점, 락 유지 시간 5분 후 자동 해제
- 마지막 방어선으로 DB에 (공연 회차, 좌석) 유니크 제약 추가
- nGrinder로 동시 5,000명 시나리오 부하 테스트 후 배포

| 항목 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 중복 판매 (공연 1회) | 3~5건 | 0건 |
| 좌석 선점 응답 p95 | 1.9초 | 0.4초 |

**Impact**
- 이후 공연 40회 연속 중복 판매 0건
- CS팀 수동 환불 업무 제거

## 사례 2: 정산 배치 처리 시간 단축

2023.01 - 2023.03 | 하늘정산 일일 정산 배치 | Spring Batch, MySQL

**Problem**
- 가맹점 1만 2천 곳의 일일 정산 배치가 3시간 40분 소요
- 새벽 배치가 아침 9시 이후까지 이어져 가맹점 정산 조회가 늦어짐

**Process & Solution**
- 실행 계획 확인 → 거래 테이블 풀 스캔, 건별 INSERT가 병목
- (가맹점 ID, 거래일) 복합 인덱스 추가
- 1,000건 단위 청크 처리와 일괄 INSERT로 변경
- 가맹점 그룹별로 나눠 병렬 실행 (스레드 4개)

**Impact**
- 배치 시간 3시간 40분 → 35분
- 정산 조회 가능 시각 오전 9시 이후 → 오전 6시 이전

## 트러블슈팅

**문제 1. 외부 결제사 응답 지연으로 전체 API 느려짐**
- Problem: 결제사 한 곳이 10초 이상 응답하지 않자 서버 스레드가 모두 대기 상태
- Solution: Resilience4j 서킷 브레이커와 3초 타임아웃 적용, 실패 건은 SQS에 넣어 재처리
- Impact: 결제사 장애 중에도 다른 API 정상 응답

**문제 2. 정산 내역 조회 N+1 쿼리**
- Problem: 정산 내역 100건 조회에 쿼리 101번 실행, 응답 2.3초
- Solution: fetch join과 batch size 설정으로 쿼리 2번으로 축소
- Impact: 응답 2.3초 → 0.3초
